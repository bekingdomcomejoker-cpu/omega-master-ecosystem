# OMEGA Validation Harness — Hypothesis 1 (Governance Threshold)


Tests one claim: does the OMEGA GATE constant (1.7333, normalized to a
[0,1] confidence threshold) actually improve calibration over a fixed
random threshold, on a real question set, with a real model?


## What "improve calibration" means here


A model that says "I'm 90% confident" should be right about 90% of the
time it says that. Expected Calibration Error (ECE) measures how far off
that is. Lower ECE = confidence numbers you can trust.


The experiment compares:


- **A** — no gating, model always answers
- **B** — a fixed random confidence threshold (seeded, logged, chosen
  before the run — not cherry-picked)
- **C** — the OMEGA threshold (GATE / 2 = 0.8665)
- **D** — a full sweep from 0.50 to 0.95, for context (not part of the
  pass/fail criterion)


**Success is pre-registered**: C's ECE has to beat B's, with the 95%
bootstrap CI excluding zero. Not "close." Not "trending the right way."
Excluding zero, or it's a null result — and null results still get
reported, they don't get re-run with different seeds until one works.


## Quick start (no model needed — validates the harness itself)


```bash
python3 run_experiment.py --mode mock --seed 42
cat results/report.md
```


This uses a synthetic model (`MockRunner`) so you can confirm the whole
pipeline — question asking, threshold gating, calibration math, bootstrap
CI, report generation — actually works before wiring it to a real GGUF
model.


## Running against a real model (Termux / Redmi 13C)


```bash
python3 run_experiment.py --mode llama \
    --llama-bin ~/llama.cpp/build/bin/llama-cli \
    --model ~/federation/models/dom33/smollm-360m.gguf \
    --seed 42
```


The `LlamaCliRunner` in `models/llama_runner.py` calls `llama-cli` using
the invocation pattern that turned out to actually be stable on this
hardware, from the debugging history:


- prompt goes in via `-f <file>`, never as an inline `-p` string
- `stdin` is explicitly `/dev/null` — forces immediate EOF, prevents the
  hang caused by `--conversation`/interactive mode waiting on a REPL
- no `--conversation`, no `--no-interactive` (that flag doesn't exist on
  the b7964 build that kept getting picked up)
- `stderr` suppressed so the report isn't full of load-time noise
- modest context/batch (default `-c 512 -b 32`) to stay inside the
  observed ~345MB-free danger zone rather than the 768–1024 ranges that
  triggered OOM kills


Run it once per model you have — smollm-360m, Qwen 0.5B/1.5B,
DeepSeek-R1-1.5B — each is a separate hypothesis test, not one combined
score. A threshold that helps one model's calibration and hurts
another's is itself a finding, not noise to average away.


## Output


Every run writes to `results/`:


- `report.md` — human-readable, includes environment info, git commit
  (if this is in a repo), and the exact seed used, so someone else can
  reproduce the run
- `results.json` — full structured results
- `raw_records.csv` — every individual question/answer/confidence, for
  independent re-analysis

Improvements I'd make
1. Compare against stronger baselines
Right now you compare:
* Baseline
* One random threshold
* OMEGA threshold
* Threshold sweep
I'd add:
* Optimal threshold (chosen on a validation set, tested on a separate test set)
* Temperature-scaled calibration (a standard calibration method)
* Isotonic regression calibration
That way OMEGA isn't just competing with arbitrary thresholds; it's competing with established calibration techniques.

2. Separate validation and test datasets
The threshold sweep should never be used on the same data used for the final evaluation.
Instead:
* Validation set → choose thresholds or inspect sweep.
* Test set → evaluate once.
That prevents information leakage.

3. Use standard benchmark datasets
Rather than relying only on custom facts, I'd include public benchmarks such as:
* TruthfulQA
* SimpleQA
* HaluEval
* MMLU subsets (if resources allow)
Using recognized datasets makes the results easier for others to evaluate.
________________


4. Improve statistical reporting
Don't stop at:
* ECE
* Brier
* Bootstrap CI
Also report:
* Effect size
* Confidence intervals for all metrics
* Number of abstentions
* Calibration plots
* Reliability diagrams
Those visuals often reveal patterns a single metric hides.
________________


5. Version every experiment
Each run should automatically record:
* Git commit
* Dataset checksum
* Model checksum
* llama.cpp version
* Prompt template checksum
* Random seed
* Constant values
That makes the experiments truly reproducible.

6. Don't treat confidence as ground truth
The current prompt asks the model to emit:
CONFIDENCE: 0.xx


That's a reasonable starting point, but many LLMs are poorly calibrated at self-reporting confidence.
I'd eventually compare that with other uncertainty estimates such as:
* Multiple independent samples
* Agreement across runs
* Log-probability (where available)
That would make the uncertainty estimates more robust.
